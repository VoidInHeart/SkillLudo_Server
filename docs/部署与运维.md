# SkillLudo 服务器部署与运维

目标是通过 `ssh SEBaseline` 连接的 Ubuntu 24.04 主机（公网 `81.70.145.148`）。保留现有 k3s 控制平面、Traefik 与 metrics-server，在独立 `skillludo` 命名空间部署当前服务端。旧 `edu-platform-prod` 业务已缩容为零，原 PV、配置及完整冷备份保留。

## 部署结构

- 公网 WebSocket：`ws://81.70.145.148`，由 Traefik 的 80 端口转发到 Service/server:3000；3000 和 MySQL 3306 不直接开放公网。
- `GET /healthz` 检查进程，`GET /readyz` 检查数据库并返回当前提交 `revision`。默认根路径的 HTTP 请求返回 404，它不是前端网页。
- Node 单副本：请求 200m CPU / 192 MiB，限制 1 CPU / 768 MiB，Node 堆上限 512 MiB。容器非 root、只读根文件系统、无 ServiceAccount 令牌；`/app/config` 使用独立 PVC 保留校准。
- MySQL 8.4：请求 100m CPU / 256 MiB，限制 1 CPU / 640 MiB，buffer pool 128 MiB，连接上限 80。独立 2 GiB PVC，应用连接池为 8。数据卷容量声明不是 local-path 的磁盘硬配额，仍需监控宿主盘。
- 数据库凭据在 k3s Secret `skillludo/mysql-credentials` 中现场随机生成，与本机开发数据库的密码分离。CI 不需要数据库 root 或应用密码。

棋局保存在 Node 进程内存中，因此明确使用 `replicas: 1` 与 `Recreate`。更新镜像会关闭旧 WebSocket（1012），在线房间与棋局不会跨版本恢复；账号、持久会话和校准文件保留。不要通过直接加副本来扩容；需要先实现共享房间存储或按房间分片。

## GitHub 配置：已经填好

仓库：`VoidInHeart/SkillLudo_Server`。入口：Settings → Environments → **production**；分支规则只允许 `main`。

| 类型 | 名称 | 应填写的内容 / 当前状态 |
| --- | --- | --- |
| Environment Secret | `DEPLOY_SSH_KEY` | 专用 `skillludo-deploy` 账号的完整 OpenSSH 私钥，包含 BEGIN/END 行和真实换行；本次已生成并保存，无需手工填写 |
| Environment Secret | `DEPLOY_KNOWN_HOSTS` | 通过现有可信 SSH 连接读取的服务器 Ed25519 公钥，采用 known_hosts 格式：`81.70.145.148 ssh-ed25519 <公钥>`；已保存 |
| Environment Variable | `DEPLOY_HOST` | `81.70.145.148` |
| Environment Variable | `DEPLOY_USER` | `skillludo-deploy` |

私钥不放进仓库、文档或聊天。GitHub 不会返回已保存的 Secret 明文；如果将来丢失本地副本，生成新密钥并同时更新服务器 `authorized_keys` 和 `DEPLOY_SSH_KEY` 即可。服务器主机密钥变更时，经可信 SSH 核实后更新 `DEPLOY_KNOWN_HOSTS`，不要关闭主机校验。

专用部署公钥带 `restrict` 和强制命令；账号没有普通 Shell、端口转发或任意 sudo 权限，只能调用 root 拥有的 `/usr/local/sbin/skillludo-ci-receiver` 并传入 `deploy <40 位提交 SHA>`。日常运维仍使用现有 `ssh SEBaseline`。

## CI/CD 行为

1. PR、main push、手动运行触发 `.github/workflows/ci-cd.yml`。官方 Actions 使用完整提交 SHA；默认 token 只有 contents:read。
2. 服务端执行类型检查、34 项回归、前后端契约检查和 build；配套客户端在固定提交 `6a8c4c8` 执行测试类型检查和 12 项纯逻辑测试。修改协议时需要同时更新配套客户端提交。
3. 构建 `skillludo/server:sha-<commit>` 镜像，排除 `.env`、密钥、日志与本机依赖。镜像压缩包作为 GitHub artifact 保留 7 天。
4. 只有 main 的非 PR 运行进入 production。通过固定主机公钥校验的 SSH 上传镜像，不在服务器安装 GitHub runner，不把普通运维 SSH 私钥交给 Actions。
5. 接收器限制上传大小、串行发布、导入本机 containerd，更新固定 Deployment/server。等待就绪后在 Pod 内执行真实双连接冒烟：认证、心跳、开房、选色、双骰和选择结果；失败时尝试回退旧镜像。
6. GitHub 再从公网检查 `/readyz` 与本次 SHA。公网检查失败会将工作流标为失败；它不会自动撤回已经通过 Pod 内检查的服务，以免把公网链路问题误判成应用故障。

数据库版本、schema、网络策略和部署资源由运维审核后单独应用，日常 CD 只更新应用镜像。容器记录在 `/opt/skillludo/releases/current-image` 和 `previous-image`；旧容器镜像不自动清理，定期查看磁盘，仅清理明确不再用于回退的版本。

## 日常命令

进入 `ssh SEBaseline` 后：

```sh
sudo kubectl -n skillludo get pods,pvc,ingress
sudo kubectl -n skillludo logs deployment/server --tail=100
sudo kubectl -n skillludo top pods
curl --fail http://127.0.0.1/readyz
sudo cat /opt/skillludo/releases/current-image
```

本地冒烟与受控压测（从服务端仓库执行）：

```powershell
$env:SMOKE_URL = 'ws://81.70.145.148'
node scripts/smoke.mjs
$env:LOAD_URL = 'ws://81.70.145.148'
$env:LOAD_ROOMS = '5'
$env:LOAD_SECONDS = '60'
$env:LOAD_STEP_MS = '700'
node scripts/load-test.mjs
```

压测会创建真实临时游客房间，四个连接一房间；结束主动退出。只在允许测试的环境执行，生产有玩家时避开压测和发布。容量结果以配套容量报告为准，不能只用空连接数估计可玩的并发人数。

## 恢复旧服务

有效旧业务快照路径保存在 `/opt/skillludo/backups/legacy-snapshot-path`；本次成功快照为 `edu-before-skillludo-20260909T061247Z`，包含原副本数、Ingress、命名空间配置、PV 定义，以及 MySQL/MinIO 的停机后文件备份。其父目录仅 root 可读；包含旧业务 Secret，不能上传公开仓库。

恢复前先暂停 SkillLudo 的 GitHub 工作流，防止下一次 push 把新服务重新拉起。将本仓 `deploy/restore-legacy.sh` 上传服务器后以 sudo 执行，它会停止 SkillLudo、恢复旧副本数与入口，使用保留的原始数据卷；它不覆盖数据库文件。此恢复脚本需在计划切回旧服务时执行，本次交付不执行旧业务恢复。

`deploy/prepare-host.sh` 是本次迁移的首次准备脚本，包含旧业务停服，不是日常发布命令，不应再次直接运行。当前主机已经完成迁移准备；新主机必须按其实际旧资源和路径调整，不能照抄 SEBaseline 的历史目录。

公网 IP 按用户选择暂时使用 WS/HTTP。微信正式发布前仍需自己的域名、WSS 证书、微信合法域名和真实身份校验；本次没有配置域名或宣称通过微信真机验收。

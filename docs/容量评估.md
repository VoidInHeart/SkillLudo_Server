# SEBaseline 服务器容量评估

日期：2026-09-09。游戏负载测试版本：`263459568ab3c00c3164632a41844bd724cd3229`。原始 JSON 和逐秒资源数据见 [capacity](capacity/README.md)，运维和 GitHub 配置见 [部署与运维](部署与运维.md)。

## 结论

**当前公网链路建议先按 4 个同时活跃的四人房间，即 16 人，保留约 30% 带宽余量。** 5 房间 / 20 人在本轮测试中流畅，但余量较少；6 房间开始出现明显尾延迟；15 房间出现超时。该建议针对本轮较密集的 700 ms 阶段节奏，不是账号注册总量，也不是空闲长连接上限。

程序本身的处理能力明显高于当前公网可用带宽：单副本、1 核 CPU 配额下，内网 500 房间 / 2000 条实际游戏连接运行 60 秒无错误；此时 CPU 已到配额上限，成功请求 P95 45.73 ms。**这不能解释为当前公网可以流畅支持 2000 人。** 若带宽充足，按内网测试保留余量可先以 250 房间 / 1000 人作为待长时间验证的处理能力目标。

## 环境与方法

| 项目 | 配置 |
| --- | --- |
| 主机 | Ubuntu 24.04，4 vCPU（AMD EPYC 7K62 虚拟核），3659 MiB RAM |
| 磁盘 | 40 GiB 系统盘；测试后约 12 GiB 可用，旧业务数据与备份保留 |
| 平台 | 单节点 k3s，Traefik 80 端口，MySQL 8.4.8 |
| 游戏容器 | 1 副本，CPU 上限 1 核，内存上限 768 MiB，Node 堆上限 512 MiB |
| 数据库 | CPU 上限 1 核，内存上限 640 MiB，buffer pool 128 MiB，应用连接池 8 |
| 空闲基线 | Node 约 30 MiB、MySQL 约 186 MiB，主机约 1.9 GiB 可用内存 |

发生器每个房间建立四条独立 WebSocket，执行真实开房、准备、开局、双骰、选点和移动，所有玩家每约 10 秒心跳。每个游戏阶段间隔 700 ms，额外发一次 `RECONNECT` 取得权威快照；没有强制骰子或 AI 代替玩家。此额外快照使测试比正常客户端更耗流量。

这是等待响应后继续发命令的闭环测试：拥塞时发送节奏会变慢，所以同时报告完成速率和失败，不能仅看连接数。下行 Mbps 是发生器收到的应用层消息，不包括 TCP/IP 开销。本轮使用明文 WS，没有测试 TLS 开销。内网发生器为同节点独立 Pod；资源采样从宿主机读取游戏容器的 cgroup 与进程，Node RSS 不包含发生器。

## 内网游戏负载

CPU 为稳定负载窗口平均值，1.0 表示一个完整 CPU 核；RSS 为该窗口峰值。

| 房间 / 连接 | 持续 | 成功命令/s | P95 / P99（ms） | Node 平均 CPU | Node RSS 峰值 | 下行 Mbps | 失败 |

| 100 / 400 | 45.70 s | 315.83 | 1.50 / 2.32 | 0.186 核 | 99.51 MiB | 35.441 | 0 |
| 250 / 1000 | 45.70 s | 789.51 | 2.10 / 4.91 | 0.432 核 | 124.16 MiB | 88.632 | 0 |
| 500 / 2000 | 60.70 s | 1575.53 | 45.73 / 82.59 | 0.856 核 | 151.57 MiB | 174.150 | 0 |

500 房间时逐秒 CPU 峰值 1.0004 核，稳定窗口记录 41 个 CPU throttling 周期；Node 内存仍有余量，宿主机最低约 1774 MiB 可用。测试期间游戏服务未重启。继续增加房间已经会受单核配额和 Node 主事件循环影响，因此本轮没有继续增加到导致服务崩溃。

## 公网游戏负载

公网发生器位于本机 Windows，经 `ws://81.70.145.148` 与 Traefik 访问。同一档位所有房间都在实际推进。

| 房间 / 人数 | 持续 | 成功命令/s | 成功请求 P95 / P99（ms） | 下行 Mbps | 失败房间 / 超时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 / 16 | 120.71 s | 12.43 | 11.92 / 35.10 | 1.384 | 0 / 0 |
| 5 / 20 | 45.60 s | 15.31 | 11.61 / 13.73 | 1.702 | 0 / 0 |
| 6 / 24 | 61.66 s | 15.67 | 255.57 / 1730.20 | 1.746 | 0 / 0 |
| 15 / 60 | 47.80 s | 18.75 | 1600.60 / 5425.97 | 1.955 | 6 / 6 |

15 房间的超时包含心跳、选骰、选棋子和状态请求；超时请求不计入成功延迟分位数，因此不能只引用 P95。完成速率没有随房间数成比例增加，下行接近 2 Mbps，同时服务器仍只有很低 CPU 使用率、无重启。这支持“当前公网路径存在约 2 Mbps 的有效带宽瓶颈”的判断。

尚未读取云控制台的套餐/带宽配置，也没有跨地区、多运营商复测；无法仅凭以上结果确定瓶颈由云套餐、出口策略还是测试路径造成。宿主机 `tc qdisc` 没有发现显式限速规则。这里记录的是实测可用链路，不能把约 2 Mbps 写成已确认的云套餐参数。

按本轮平均每房间约 0.35 Mbps 的下行量、保留 30% 余量，可用 `同时活跃房间数 ≈ floor(可用 Mbps × 0.7 / 0.35)` 做初步预算。例如实测可用带宽提升到 10 Mbps 时约 20 房间，20 Mbps 时约 40 房间；这是同一负载模型下的估算，升级后应重新验证。优先确认和改善公网带宽；更换 CPU 或增加 k3s 副本不能解决当前观测到的流量瓶颈。

## 数据库账号链路

使用真实生产数据库，32 个新建临时账号，并发 4，完成注册、登录和新连接恢复，共 4.64 秒。测试发生器通过 stdin 在游戏 Pod 内运行，因此与服务共享 CPU 配额；所有测试账号及其外键关联记录随后清理并验证为零。

| 操作 | 次数 | P50 | P95 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| 注册（含 scrypt 与数据库写入） | 32 | 293.88 ms | 320.11 ms | 380.03 ms |
| 登录（含 scrypt 与会话写入） | 32 | 284.52 ms | 369.57 ms | 370.48 ms |
| 同一进程内的新连接恢复 | 32 | 1.48 ms | 4.70 ms | 69.54 ms |

注册/登录的突发负载需要额外 CPU 余量；此混合测试不是独立登录接口的极限 QPS。新连接恢复没有重启服务，不代表已经验证跨服务器或跨进程的棋局恢复。

## 当前边界与后续验证

- 这是 45–120 秒的短时测试，不是数小时或数天的稳定性证明，也没有验证大量 AI 托管、微信真机、WSS、多地域或断网风暴。
- 当前 `SessionManager` 的游客会话 Map 没有 TTL 淘汰；房间清理后旧游客会话仍可能累计到服务重启。长期开服前需要补会话回收并进行长时间测试。
- 房间与对局在单进程内存中，发布/重启会中断棋局。横向扩容前需要共享状态或按房间分片，不能直接将副本数改为 2。
- 后续可以减少重复完整快照、采用增量状态广播；每次改协议都需两仓同步并重跑公网负载，以实测新的每房间带宽。

当前可执行的保守规划是 **4 房间 / 16 人同时活跃**，5 房间作为已短测通过但余量较少的档位；在线大厅和空闲连接应另行测量。报告给出容量建议，尚未在业务中新增全局房间准入上限。
